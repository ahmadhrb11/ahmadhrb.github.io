# نظام متابعة طلبات المتدربين

## الأدوار والصلاحيات

### 1) المتدرب — بدون تسجيل دخول

- يقدّم طلبًا من الصفحة العامة **`/submit`**.
- يتابع طلباته من **`/track`** بإدخال **الرقم التدريبي فقط** (بدون رقم مرجعي).
- يرى قائمة **جميع** طلباته وحالة كل منها، ويفتح أيًّا منها لرؤية المحادثة كاملة.
- يستطيع كتابة ردود جديدة طالما الطلب «قيد المعالجة» أو «مُصعّد لوكيل التدريب».

### 2) مسؤول النظام (Admin) — `/admin`

- يرى **جميع** الطلبات وجميع المحادثات من كل الأطراف بلا استثناء.
- عدّاد/إشعار واضح بعدد الطلبات **«قيد المراجعة»** التي تنتظر إجراءه.
- جدول بفلترة حسب: الحالة، النوع، التخصص، وبحث بالاسم أو الرقم التدريبي.
- شاشة تفاصيل الطلب: بيانات المتدرب + **سجل الحالة الكامل** (متى ولماذا تغيّرت، شامل التصعيد) + المحادثة بترتيب زمني.
- أزرار: **موافقة** (تحويل تلقائي لرئيس القسم) · **رفض** (بسبب إلزامي) · **إنهاء الطلب**.
- صفحة إعدادات **`/admin/settings`**: إضافة/تعديل التخصصات وربطها برؤساء الأقسام، وإدارة حسابات الموظفين.

### 3) رئيس القسم (Department Head) — `/department`

- يرى **فقط** الطلبات المحوّلة إليه (حسب التخصص المرتبط به).
- عدّاد للطلبات التي تنتظر ردّه (طلبات جديدة + طلبات ردّ عليها المتدرب برسالة جديدة).
- لكل طلب: المحادثة كاملة + خانة نصية + زر إرسال — **متاح فقط** إذا كان الطلب «قيد المعالجة» ولم يُصعَّد.
- الطلبات المُصعّدة تبقى ظاهرة له **للاطلاع فقط** مع تنبيه واضح بأنها «مُصعّدة».

### 4) وكيل التدريب (Training Deputy) — `/deputy`

- حساب واحد يستقبل الطلبات المُصعّدة تلقائيًا **من أي قسم**.
- عدّاد للطلبات المُصعّدة التي تنتظر ردّه.
- يرى المحادثة **كاملة منذ البداية** — شاملة مراسلات رئيس القسم قبل التصعيد — ويكمل المراسلة مع المتدرب.

## لوحة المعلومات التحليلية

صفحة **`/admin/dashboard`** (لمسؤول النظام فقط) — قراءة تحليلية لبيانات الطلبات، بلا أي إجراءات:

- **رقم رئيسي**: الطلبات المفتوحة التي تحتاج متابعة، موزّعة على مراحلها.
- **ثمانية مؤشرات**: إجمالي الطلبات · معدل الإنجاز · معدل التصعيد · معدل الرفض · متوسط زمن الإغلاق · متوسط زمن مراجعة الأدمن · متوسط أول رد من رئيس القسم · متوسط الرسائل لكل محادثة.
- **تنبيه عملي**: الطلبات التي لم يردّ عليها رئيس القسم وتوشك على التصعيد التلقائي، مع رابط مباشر لكل طلب.
- **حركة الطلبات أسبوعيًا**: الوارد مقابل المنجز خلال آخر 12 أسبوعًا (مقياس واحد لكلتا السلسلتين).
- **توزيعات**: على الحالات (نسبة إلى الكل) · حسب النوع · حسب التخصص.
- **جدول أداء رؤساء الأقسام**: المحوّل إليه، قيد المعالجة، المُصعّد، المنتهي، متوسط أول رد، ومعدل التصعيد.
- **أقدم الطلبات المفتوحة**.

**فلتر الفترة** (30 / 90 يومًا · سنة · كل الفترات) في أعلى الصفحة يحكم كل ما تحته، عدا القسمين الموسومين بـ«لقطة لحظية» فهما يعرضان الوضع الآني دائمًا.

**ملاحظات تقنية:** كل المخططات مرسومة بـ SVG/CSS خالص بلا أي مكتبة رسم إضافية، ولكل مخطط **نسخة جدولية** قابلة للفتح («عرض القيم كجدول») فلا تبقى أي قيمة محبوسة خلف اللون. ألوان المخططات مُتحقَّق منها آليًا (نطاق الإضاءة، التشبّع، الفصل تحت عمى الألوان، والتباين مع الخلفية)، وترتيب ألوان الحالات مختار بحيث لا يتجاور الأخضر والأحمر.

## الرقم التدريبي وبريد المتدرب

### قاعدة التحقق

الرقم التدريبي يُقبل فقط إذا كان **9 خانات رقمية بالضبط** (0-9)، بلا حروف أو رموز أو مسافات.

المنطق كله في دالة واحدة مشتركة — `isValidTraineeNumber()` في `src/lib/validation.ts` — ولا يتكرّر الـ regex في أي مكان آخر. تُستخدم في:

| الموضع | الطبقة | السلوك عند رقم غير صالح |
|---|---|---|
| `/submit` | عميل | رسالة فورية أسفل الحقل + تعطيل زر الإرسال |
| `submitRequestAction` | **خادم** | `fieldErrors.traineeNumber` ولا يُنشأ أي طلب |
| `/track` | عميل | رسالة فورية + تعطيل الزر |
| `goToTrainee` (إجراء خادم) | **خادم** | إعادة إلى `/track?error=format` مع الرسالة |
| `/track/[traineeNumber]` و`/track/[traineeNumber]/[requestId]` | **خادم** | إعادة إلى النموذج قبل أي استعلام على القاعدة |

> **التحقق في الخادم لا يعتمد على العميل إطلاقًا.** إزالة `pattern` و`maxlength` من المتصفح وإرسال رقم غير صالح يُرفض في الخادم ولا يُنشئ أي صف — وهذا مُختبَر آليًا.
>
> **ملاحظة على رمز 400:** لا توجد في المشروع أي API route تستقبل هذا الحقل؛ التقديم والتتبّع كلاهما Server Actions وهي لا تحمل رموز حالة HTTP. المقابل الاصطلاحي هو إرجاع `{ ok: false, fieldErrors }` الذي يعرضه النموذج، وهو النمط المتّبع في `ActionState` عبر المشروع.
>
> **الأرقام العربية-الهندية (٠١٢…) مرفوضة عمدًا** لأن الرقم يُخزَّن ويُستخدم كجزء من رابط `/track`.

### البريد المولّد تلقائيًا

عند إنشاء أي طلب، يُبنى بريد المتدرب **في الخادم حصرًا** بصيغة:

```
{الرقم_التدريبي}@tvtc.edu.sa      مثال: 442412003@tvtc.edu.sa
```

- يُولَّد بدالة `buildTraineeEmail()` في `src/lib/validation.ts` **فور نجاح التحقق** وقبل الحفظ.
- يُخزَّن في حقل `Request.traineeEmail` (إلزامي)، ويظهر للأدمن ورؤساء الأقسام ووكيل التدريب ضمن بيانات الطلب.
- لا تصل أي قيمة له من واجهة المستخدم، ولا يمكن تعديله من أي نموذج.

**لماذا داخل `Request` لا في جدول `Trainee` منفصل؟** البريد دالة حتمية من الرقم التدريبي، فلا يمكن أن يتعارض مع مصدره — وحجّة منع التكرار المعتادة (تعارض التحديث) لا تنطبق هنا. يصبح الجدول المنفصل هو الصواب حين تظهر بيانات للمتدرب **غير مشتقّة** من رقمه (جوال، تفضيل إشعارات، اسم موثّق).

**لماذا الحقل `String` لا `Int`؟** الأصفار البادئة: الرقم `012345678` يصبح `12345678` مع النوع الرقمي — تلف بيانات صامت. ويُستخدم الرقم كجزء من مسار الرابط، وبحث الأدمن يعتمد `contains` غير المتاح على الحقول الرقمية. وهو **معرّف لا كمية**: لا تجري عليه أي عملية حسابية.

> الاستخدام المستقبلي المقصود لهذا البريد هو إشعارات حالة الطلب عبر تكامل خارجي (Power Automate). **لا يوجد أي منطق إرسال بريد في النظام حاليًا** — الحقل مخزَّن وجاهز فقط.

## سير عمل الطلب وحالاته

```
                          ┌──── موافقة الأدمن ────► قيد المعالجة ──┐
                          │     (تحويل تلقائي       (محادثة مستمرة  │
  تقديم الطلب ► قيد المراجعة     لرئيس القسم)        مع رئيس القسم)  │
                          │                                        │
                          └──── رفض الأدمن ────► مرفوض              │
                               (بسبب مكتوب)                        │
                                                                   │
        3 أيام بلا رد من رئيس القسم (مهمة مجدولة) ◄─────────────────┘
                          │
                          ▼
              مُصعّد لوكيل التدريب ──► (محادثة مستمرة مع وكيل التدريب)
                          │
                          └──── «إنهاء الطلب» يدويًا من الأدمن ────► منتهي
```

| الحالة | المعنى | من يستطيع الرد؟ |
|---|---|---|
| **قيد المراجعة** | طلب جديد بانتظار قرار الأدمن | لا أحد |
| **قيد المعالجة** | مُحوَّل لرئيس القسم، المحادثة مفتوحة | رئيس القسم + المتدرب + الأدمن |
| **مُصعّد لوكيل التدريب** | تجاوز رئيس القسم مهلة الرد | وكيل التدريب + المتدرب + الأدمن |
| **منتهي** | أغلقه الأدمن يدويًا | لا أحد |
| **مرفوض** | رفضه الأدمن مع سبب مكتوب يظهر للمتدرب | لا أحد |

### تفاصيل قاعدة التصعيد

- مؤقّت التصعيد هو الحقل `Request.lastHeadReplyAt`: يُضبط لحظة **موافقة الأدمن**، ثم لا يُحدَّث إلا عند **رسالة من رئيس القسم نفسه**.
- **ردود المتدرب لا تُعيد ضبط المؤقّت** — أي أن التأخر يُحسب على رئيس القسم فقط، تمامًا كما هو مطلوب.
- عند التصعيد: تتغيّر الحالة، وتُضاف **رسالة نظام** ظاهرة للجميع داخل المحادثة، ويُسجَّل **قيد في سجل الحالة** يوضّح الوقت والسبب.

## التشغيل محليًا

### المتطلبات

- Node.js **20** أو أحدث (مُختبَر على 22)
- npm

### الخطوات

```bash
# 1) تثبيت التبعيات
npm install

cp .env.example .env
```

```bash

```

```bash
# 3) إنشاء قاعدة البيانات وتطبيق المخطط
npx prisma migrate dev

# 4) تعبئة البيانات التجريبية
npm run db:seed

# 5) تشغيل التطبيق
npm run dev
```

افتح <http://localhost:3000>.

## اختبار التصعيد التلقائي

الطلب `442412005` مُهيأ مسبقًا بتأخير 4 أيام، فيكفي تشغيل:

```bash
npm run escalate
```

ولاختبار التصعيد على **أي طلب آخر** دون انتظار 3 أيام فعلية، توجد أداة تطوير تُرجِع مؤقّت الطلب إلى الماضي:

```bash
# إرجاع طلب محدد 4 أيام إلى الوراء
npm run simulate:delay -- <requestId> 4

# أو كل الطلبات «قيد المعالجة» دفعة واحدة
npm run simulate:delay -- --all 4

# ثم تشغيل التصعيد
npm run escalate
```

يمكن أيضًا استدعاء مسار المهمة عبر HTTP مباشرة:

```bash
curl -H "Authorization: Bearer $CRON_SECRET" http://localhost:3000/api/cron/escalate
```

## النشر المجاني على Vercel + Turso

SQLite ملفٌ على القرص، وخوادم Vercel مؤقتة (لا تحتفظ بالملفات بين الطلبات)، لذا نستخدم **Turso** — وهي قاعدة SQLite سحابية بخطة مجانية. الكود يتحوّل إليها **تلقائيًا** بمجرّد وجود متغيّري بيئة Turso، دون أي تعديل.

### 1) إنشاء قاعدة بيانات على Turso

```bash
# تثبيت أداة Turso
curl -sSfL https://get.tur.so/install.sh | bash

turso auth signup            # أو: turso auth login
turso db create trainee-requests

# احصل على رابط القاعدة
turso db show trainee-requests --url
# مثال الناتج: libsql://trainee-requests-username.turso.io

# أنشئ رمز وصول
turso db tokens create trainee-requests
```

### 2) تطبيق المخطط على قاعدة Turso

أسهل طريقة: استخرج ملف SQL من الهجرات وطبّقه على القاعدة السحابية.

```bash
# ادمج كل ملفات الهجرة في ملف واحد
cat prisma/migrations/*/migration.sql > /tmp/schema.sql

# طبّقه على قاعدة Turso
turso db shell trainee-requests < /tmp/schema.sql
```

للتحقق:

```bash
turso db shell trainee-requests ".tables"
```

### 3) تعبئة البيانات الأولية في الإنتاج (اختياري)

شغّل السكربت محليًا وهو موجَّه إلى Turso:

```bash
TURSO_DATABASE_URL="libsql://..." TURSO_AUTH_TOKEN="ey..." npx tsx prisma/seed.ts
```

> ملاحظة: سكربت التعبئة **يحذف كل البيانات الموجودة** قبل إنشاء البيانات التجريبية، فلا تشغّله على قاعدة تحتوي بيانات حقيقية.

### 4) الربط مع Vercel

1. ارفع المشروع إلى GitHub.
2. من [vercel.com](https://vercel.com) اختر **Add New → Project** واستورد المستودع.
3. اترك **Root Directory** على `./` و**Framework Preset** على Next.js (يُكتشف تلقائيًا).
4. أضف متغيّرات البيئة التالية في **Settings → Environment Variables**:

   | المتغيّر | القيمة |
   |---|---|
   | `TURSO_DATABASE_URL` | `libsql://...` من الخطوة 1 |
   | `TURSO_AUTH_TOKEN` | الرمز من الخطوة 1 |
   | `AUTH_SECRET` | ناتج `openssl rand -base64 32` |
   | `AUTH_URL` | رابط موقعك، مثل `https://your-app.vercel.app` |
   | `CRON_SECRET` | ناتج `openssl rand -hex 32` |
   | `DATABASE_URL` | `file:./dev.db` (قيمة شكلية يتطلبها Prisma وقت البناء فقط) |
   | `ESCALATION_DAYS` | `3` (اختياري) |

5. اضغط **Deploy**.

## جدولة المهمة التلقائية (Vercel Cron)

الجدولة مُعرَّفة مسبقًا في `vercel.json`:

```json
{
  "crons": [
    { "path": "/api/cron/escalate", "schedule": "0 2 * * *" }
  ]
}
```

- تعمل **يوميًا الساعة 02:00 بتوقيت UTC** — وهذا متوافق مع حدود **خطة Vercel Hobby المجانية** (مهمة واحدة يوميًا لكل مشروع).
- تُفعَّل تلقائيًا عند أول عملية نشر بعد وجود `vercel.json`؛ يمكنك مراجعتها من **Project → Settings → Cron Jobs**.
- Vercel يرسل ترويسة `Authorization: Bearer $CRON_SECRET` تلقائيًا، والمسار يرفض أي طلب بلا هذا السر.
- تشغيل يدوي في أي وقت:

  ```bash
  curl -H "Authorization: Bearer $CRON_SECRET" https://your-app.vercel.app/api/cron/escalate
  ```

  الاستجابة:

  ```json
  { "ok": true, "escalatedCount": 2, "escalatedIds": ["..."], "thresholdDays": 3, "checkedAt": "..." }
  ```

> **بدائل مجانية للجدولة** إن لم ترغب في Vercel Cron: [cron-job.org](https://cron-job.org) أو GitHub Actions مع خطوة `curl` تستدعي نفس المسار بنفس الترويسة.

## متغيّرات البيئة

| المتغيّر | إلزامي؟ | الوصف |
|---|---|---|
| `DATABASE_URL` | نعم | مسار ملف SQLite محليًا، مثل `file:./dev.db` |
| `AUTH_SECRET` | نعم | مفتاح توقيع جلسات NextAuth |
| `AUTH_URL` | في الإنتاج | رابط الموقع الكامل |
| `AUTH_TRUST_HOST` | لا | مضبوط أصلًا في الكود (`trustHost: true`) ليعمل خارج Vercel أيضًا — لا حاجة لضبطه |
| `CRON_SECRET` | مُستحسن | حماية مسار `/api/cron/escalate` (إن تُرك فارغًا يصبح المسار مفتوحًا — للتطوير المحلي فقط) |
| `ESCALATION_DAYS` | لا | مهلة التصعيد بالأيام (الافتراضي `3`) |
| `TURSO_DATABASE_URL` | في الإنتاج | عند وجوده يتحوّل التطبيق تلقائيًا إلى Turso |
| `TURSO_AUTH_TOKEN` | في الإنتاج | رمز الوصول لقاعدة Turso |

## ملاحظات أمنية

- صفحة `/track` تعتمد على **الرقم التدريبي وحده** كما هو مطلوب في المواصفات — أي أن من يعرف رقم متدرب يستطيع رؤية طلباته والرد نيابةً عنه. إن أردت تشديدها لاحقًا، أبسط الخيارات: مطابقة الاسم مع الرقم، أو رمز وصول قصير يُعطى للمتدرب عند التقديم.
- كلمات المرور مُخزّنة بتجزئة **bcrypt**، والجلسات موقّعة بـ JWT عبر `AUTH_SECRET`.
- كل صفحات لوحات التحكم محمية بحارس دور على مستوى الخادم (`requireRole`)، وكل استعلامات رئيس القسم مقيّدة بـ `assignedHeadId`، فلا يستطيع فتح طلب قسم آخر حتى بتعديل الرابط يدويًا.
- جميع الـ Server Actions تتحقق من الصلاحية ومن حالة الطلب قبل أي تعديل، ولا تعتمد على إخفاء الأزرار في الواجهة.
